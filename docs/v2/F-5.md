## Meta readers that flush first

Found with `grep -rn "metaRef\|\.meta()\|host\.meta\|SYNC_FIELD\|serializeStored\|docOnlyJson\|makeBackup" src`:

| Reader | How it flushes |
|---|---|
| `persist(d)`, used by the debounced save, the unmount save and the background microtask (`MandaratContext.tsx:320-323`) | `flushStamp()` before `serializeStored` |
| `SyncPort.meta()`, `updateMeta()`, `replica()`, `applyRemote()`, `adopt()`, `epochReset()` (`syncEnvelope.ts:183-234`) | `host.flush?.()` at the top of each. The store passes `flush: flushStamp` (`MandaratContext.tsx:867`). This covers every engine read: `readRemotes`, `push`, `pull`, `removeStale`, `cycle`, `decide`, `apply`, `boot` rekey, `background`, `ownName` and `createSyncEngine`'s first status. |
| `SyncPort.epoch()` (new, used by `ICloudSync`) | Does **not** flush, on purpose. Stamping never changes the epoch, and flushing on every doc change would put the clock copy back on each edit. |
| `SyncPort.keepCopy()` | Reads the doc only; no flush needed |
| `commit(next, 'epoch' \| 'none')` (`putMerged`, load, `undoReset`, `resetAll`) | `commitMeta` runs `stampPending` first |
| `resetAll`, `undoReset` | `flushStamp()` first, so the saved pre-reset meta is complete |
| Load (`openStored`) | Stamps the rollover eagerly (once per launch); `metaRef` is then set and committed with `'none'` |
| Daily snapshot `writeSnap`, `keepSnapshot` | `docOnlyJson`, which has no meta. No flush needed. |
| Backup export (`shareFile.ts` → `makeBackup(doc)`) | Doc only, with no meta. No flush needed. |

Tests that pinned the eager form on purpose, now changed to "stamped by the next persist or port read":
- `tests/syncEnvelope.test.js` `source: the store stamps lazily …`. It replaces `source: the store stamps in commit only through stampCommit`, the pin V3-E §5 mentions. It now pins `commitMeta` in `commit`, `stampPending` in `flushStamp`, a flush at the top of every port method, and flushes in `persist`, `resetAll` and `undoReset`.
- `tests/syncEnvelope.test.js` `a pull that finishes late …`. It read `A.meta.clock` straight after edits. It now reads `A.port.meta()` (a port read, which flushes) before taking the start clock and the typed paths. The assertions are unchanged.
- The two store mirrors (`storeSim` in `syncEnvelope.test.js`, `makeDevice` in `syncEngine.test.js`) commit through `commitMeta` and flush through the port's `flush` hook and on persist (`kill`). They also flush when time moves on, because the store persists within 300 ms of an edit. In the `syncEngine` mirror this is a `world.wall` setter. In `syncEnvelope`, `world.tick()` flushes each device with probability 0.8, so edits are sometimes still pending at the next step, as in a burst.

## Deviations

1. **Undo restores more than `epoch`.** `undoResetMeta` restores `epoch`, `clock`, `parts` **and `seen`** from before the reset. It keeps the current `dev`/`tag`/`vendor`, `enabled`, `account`, `last`, `pushed`, `pulledAt` and `gcDay`. `seen` comes back so that a file read between reset and undo is read again: its stamps were merged into the reset clock, which is being thrown away. `enabled` is kept so that an undo never turns sync back on after the user turned it off in the window. `last` is kept so the clock never runs backwards. The reviewer's condition was "revision unchanged and `pushed` unchanged". I also require "the epoch is still the reset epoch", because a higher epoch pulled in the window must not be undone, and "the snapshot is the doc the reset saw". To make the second check exact, `doReset` now uses `getDoc()` instead of the rendered `doc`.
2. **The epoch-delay rule lives in `ICloudSync` only**, as asked. A push from another engine path in the window still sends the reset epoch: an `onChange`-driven cycle, when another device writes during the 8 s, or a foreground cycle. The undo then falls back to `replaceDoc`, which is today's behaviour. An `onChange` cycle that changes the doc also bumps the revision, and then the undo is refused anyway. Background pushes are accepted, as the reviewer allows. With VoiceOver on, the toast stays until it is dismissed, so a push after 10 s makes the undo a `replaceDoc`.
3. **`syncCommitBase.ts`**, a third new file beside the two named in the task (it matches `syncCommit*.ts`). Without it, the web stubs would have to duplicate `serializeStored`, `docOnlyJson` and the constants, or import `syncEnvelope` and pull the merge code back in. `syncEnvelope.SYNC_FIELD`, `serializeStored` and `docOnlyJson` stay importable from `syncEnvelope` (re-exported), so callers and tests did not change.
4. **The timing guard measures the commit's meta step (`commitMeta`)**, not the action's own doc transform. On `heavyDoc()`, `toggleCountToday` alone is about 0.5 ms median here, which is not stamping. Timing it with the commit would make the guard flaky without guarding anything.
5. **`heavyDoc()`** moved from `tests/syncMerge.test.js` to `tests/helpers/heavyDoc.js`, so the merge timing test and the new commit guard use the same doc.
6. **`converge` in `tests/syncMerge.test.js` runs to a fixpoint** (up to 8 rounds, convergence still asserted). This is not one of the two oracle fixes R-1 described. Without it the suite cannot pass at 50,000 seeds; see the fuzz section.
7. **R-8 #3 optional step 3 (no meta until sync is first enabled): skipped.** Today the store's meta is what creates the port (`portOn`), and the engine runs entirely through `port.updateMeta`/`port.meta()`. That covers rekey at boot, `setEnabled`/`decide`/`apply` writing `enabled: true` and `account`, the replica's file name (`meta.dev`) and the `ownName` for the probe. All of these do nothing without a meta. Deferring the meta would need a new "create meta on enable" path through the port and the engine, with `epochReset` of the whole doc, taken before `keepCopy` and the choice. That path also touches rekey, the onboarding probe, and backup restore or relaunch with no `_sync`. I could not show with this package's tests that every one of those paths stays correct, so I left it out, as the task allows. With the lazy stamp, the per-tap cost is gone for every iOS user. What remains for never-sync installs is the stored clock size (about 4×) and one `stampLocal` per 300 ms-debounced persist, off the tap frame.

## Fuzz at 50,000 seeds (R-1 F8)

Run in 4 shards of 12,500 seeds each (`FUZZ_SEEDS=12500 FUZZ_FROM=1|12501|25001|37501`, seeds 1–50,000) on 4 cores:

| Test | Result |
|---|---|
| counters are conserved (instrumented clip) | **pass** on all 4 shards, about 23 min per shard |
| never loses an edit, first run (with only the two fixes R-1 asked for) | **fail**, a third class. The first failures were seeds 1203, 14019, 25449 and 38650, each at `converged`, not at a value. The `x/<id>/done` class that used to fail first (seed 509, …) no longer appears. |
| never loses an edit, after the `converge` fix below | **pass** on all 4 shards, about 15 min per shard |

**The third class is the test's `converge`, not the merge.** `world().pull` runs `materialize` at random (half the pulls). `materialize` can issue new local stamps, for example M1 adding the day-log key of a count log. `converge` did exactly two hub rounds. When the last pull of the last round materialized, that device held stamps nobody else had yet, so the replicas differed. Seed 1203 shows this: after 2 rounds dev 1 has `d/2026-11-13/5-3`, `d/2026-11-19/2-xa1` and `d/2026-12-16/5-3` stamped and dev 0 does not, and after 3 or more rounds they are equal. R-1 reported "no unconverged world" for its categorised rerun, so its scaled copy probably differed in its loop bounds. Fix (`tests/syncMerge.test.js:264-279`): `converge` keeps doing hub rounds until every replica key is equal, up to 8 rounds. The `converged` assertion is unchanged, so the test still fails on a world that does not converge. The four seeds above pass, and the default 150-seed run is unchanged (20/20 in the file).

How to rerun: `FUZZ_SEEDS=12500 FUZZ_FROM=<1|12501|25001|37501> node --test --test-name-pattern="never loses an edit|counters are conserved" tests/syncMerge.test.js`, one shard per core.
