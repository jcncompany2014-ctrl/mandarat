## Findings

### 1. P1 — Native Sentry events and sessions carry an installation ID; the App Privacy answer and the policy do not match

**Where**
- `src/lib/crash.native.ts:83-96` (the `Sentry.init` options);
- `app.json:65-75` (`NSPrivacyCollectedDataTypes`: CrashData only);
- `docs/v2/privacy.md:33`, `:84` and `:135` (ko, ja and en: "no user ID"), and `:183` (the App Privacy answers);
- `docs/RELEASE_CHECKLIST.md:86-87`.

**Evidence.** `@sentry/react-native` 7.11 pins `Sentry/HybridSDK 8.58.0` (`node_modules/@sentry/react-native/RNSentry.podspec:49`). The sentry-cocoa 8.58.0 source was fetched to `/tmp/r8` and shows three things:
- `SentryClient.m:826` calls `setUserIdIfNoUserSet:` on every native event: crashes, app hangs and watchdog terminations.
- `SentryClient.m:979-987` then sets `user.userId = [SentryInstallation idWithCacheDirectoryPath:…]`, a random UUID that lasts for the life of the install.
- `SentryHub.m:105-109` gives every auto-tracked session `distinctId = SentryInstallation id`. `enableAutoSessionTracking` is on by default and is not turned off in `crash.native.ts`. So one session envelope is sent each time the app opens, not only when it crashes.

These native envelopes never pass through the JS `beforeSend`, so `scrubEvent`'s `delete event.user` cannot remove the ID. JS-origin events are fine: their `user` is deleted (simulation below).

Sentry-cocoa's own `Sources/Resources/PrivacyInfo.xcprivacy` at 8.58.0 declares `CrashData`, `PerformanceData` and `OtherDiagnosticData` (not linked, not tracking, App Functionality). Xcode merges that manifest into the app's privacy report. The app's own manifest, the policy (`privacy.md:183`) and the release checklist declare Crash Data only.

The policy also says the app sends a report only "when the app stops or hits an error" (`privacy.md:31`, `:82`, `:133`). The per-launch session ping makes that statement false.

**Fix** (owner files: `src/lib/crash.native.ts`, `tests/crash.test.js`, `app.json`, `docs/v2/privacy.md`, `docs/RELEASE_CHECKLIST.md`):
1. In `Sentry.init`, add `enableAutoSessionTracking: false`. This stops the per-launch session ping and its `did`. In `tests/crash.test.js` (the init test, near line 130), add `assert.equal(o.enableAutoSessionTracking, false);`.
2. The installation ID on native crash, hang and watchdog events cannot be removed from JS. Keep the events, and make the documents true:
   - `app.json` › `privacyManifests.NSPrivacyCollectedDataTypes`: add `NSPrivacyCollectedDataTypePerformanceData` (app hangs) and `NSPrivacyCollectedDataTypeOtherDiagnosticData` (breadcrumbs, device model and OS). Use the same flags as CrashData (`Linked: false`, `Tracking: false`, `AppFunctionality`), matching Sentry's manifest.
   - `privacy.md:183` and `RELEASE_CHECKLIST.md:87`: in App Privacy, declare **Diagnostics › Crash Data, Performance Data and Other Diagnostic Data**, each "not linked, not tracking, App Functionality".
   - `privacy.md:33`, `:84` and `:135`: remove "user ID / 사용자 식별자 / ユーザーID" from the not-sent list. Add a line to the sent list:
     - en: "a random ID that Sentry creates for this installation, so that repeated crashes can be counted. It is not linked to you and is deleted when you delete the app."
     - ko: "같은 오류가 몇 번 났는지 세려고 Sentry가 이 설치마다 만드는 임의의 번호(사용자와 연결하지 않으며, 앱을 지우면 사라져요)."
     - ja: "同じエラーの回数を数えるためにSentryがインストールごとに作る無作為の番号(利用者とは結び付けず、アプリを削除すると消えます)。"
   - In the sent list, also add "the app freezing (a hang) and its location in the code".
   - Update the reviewer table row "Sentry: what is sent" (`privacy.md:174`) to match.
3. Device QA (RELEASE_CHECKLIST, V4-F list): on a preview build, force a native crash and confirm in Sentry that the event shows `user.id` set to a UUID and no name, e-mail or IP. Confirm that no sessions arrive after step 1.

### 2. P1 — Kept breadcrumbs are not scrubbed: the ErrorBoundary console crumb leaks the quoted text

**Where**
- `src/lib/crash.native.ts:34-43` (`keepCrumb` checks length only);
- `src/lib/crash.native.ts:59-61` (`scrubEvent` re-applies `keepCrumb` only);
- the trigger at `src/components/ErrorBoundary.tsx:69` (`console.warn('Mandarat crashed', error)`), which runs just before `crash.report(error)` on `:71`.

**Evidence.** `/tmp/r8/sentry-sim.js` builds events with the real `@sentry/core` (`eventFromUnknownInput`, `eventFromMessage`). It builds the console breadcrumb exactly as the core console integration does: `message: safeJoin(args, ' ')`, `level: severityLevelFromString('warn')`. It then runs both through the real `crash.native.ts` (`keepCrumb`, then `scrubEvent`):

```
## ErrorBoundary: quoted doc text in error
 leaks: 매일 아침 30분 달리기 | 매일 아침
 exception.value: "Cannot find cell \"…\""
 breadcrumbs: [{"c":"console","m":"Mandarat crashed TypeError: Cannot find cell \"매일 아침 30분 달리기\""}]
 tags: {"lang":"ko","pro":"n","layout":"phone"}
```

The exception value is scrubbed. The `console` crumb is a `warning` that is 62 characters long, under the 80-character limit, so it is kept verbatim in the same event. `[ShareChart]`, `[print]`, `[store]` and the other `console.warn(…, e)` calls in `src/**` have the same shape. They are listed in the grep under "Verified" below.

**Fix** (owner files: `src/lib/crash.native.ts`, `tests/crash.test.js`). In `keepCrumb`, scrub every message that is kept:

```ts
export function keepCrumb(b: Breadcrumb): Breadcrumb | null {
  if (b.category === 'console' && !KEEP_CONSOLE.has(String(b.level ?? 'log'))) return null;
  if (typeof b.message === 'string' && b.message.length > MAX_CRUMB) return null;
  const out: Breadcrumb = typeof b.message === 'string' ? { ...b, message: scrubText(b.message) } : { ...b };
  // console 기록의 인자(객체 그대로)는 보내지 않는다
  if (out.category === 'console') delete out.data;
  return out;
}
```

Test: add a crumb `{ category: 'console', level: 'warning', message: 'Mandarat crashed TypeError: Cannot find cell "매일 아침"' }` to `koreanEvent()` in `tests/crash.test.js`. Assert that `'매일 아침'` does not appear in `JSON.stringify(ev)` and that the crumb's message ends with `"…"`.

The `'short'` expectation in the existing test still holds.

### 3. P1 — Stamping costs 6–10 ms per commit (budget: under 1 ms), and the clock makes the stored doc 4× larger for all iOS users

**Where**
- `src/lib/syncLocal.ts:198-209`: `stampLocal` calls `copyClock(meta.clock)`, an O(clock) copy, on every commit;
- `src/store/MandaratContext.tsx:252-256`: `commit` runs `stampCommit` synchronously on every update;
- `src/store/MandaratContext.tsx:29-30` and `:343`: a meta, and therefore stamping, exists on every iOS install, even with sync off. `gc()` runs only inside an enabled sync cycle (`syncEngine.ts:500`), so the clock of a user who never syncs only grows.

**Evidence.** `/tmp/r8/perf.js` uses the same `heavyDoc()` as `tests/syncMerge.test.js:686`, with Node v22.22.0 (V8 JIT):

```
3-year doc: 22666 paths, clock 22666 keys, stored JSON 1149 KB (doc only 282 KB)
changedPaths · cell text (one keystroke-sized edit) median 0.40 ms  p90 0.51 ms
stampCommit (full) · cell text                      median 7.79 ms  p90 9.15 ms
changedPaths · today check (dayLog toggle)          median 0.31 ms  p90 0.43 ms
stampCommit (full) · today check (dayLog toggle)    median 6.13 ms  p90 8.14 ms
changedPaths · count +1                             median 0.82 ms  p90 1.22 ms
stampCommit (full) · count +1                       median 10.20 ms p90 12.16 ms
stampCommit (full) · reflection text                median 9.78 ms  p90 11.39 ms
persist: serializeStored (JSON of doc + _sync)      median 11.45 ms p90 12.78 ms
```

Finding the changed paths fits the budget (0.1–0.8 ms). The clock copy does not: it is 10–20× over budget.

Hermes on the device has no JIT, so a check-off tap should be expected to spend tens of milliseconds in this copy. That is over one frame, and it lands on the tap's own frame. The stored JSON grows from 282 KB to 1149 KB, and each 300 ms-debounced persist re-serializes and writes all of it. V2-F handoff 1c and V3-E §5 already flagged this as a risk.

Text inputs commit on idle (`Today.tsx:578-583` `IDLE_MS`, `ActionSheet.tsx:501-505` `MEMO_IDLE`), not on every keystroke. So the cost is paid per tap and per idle commit, not per character.

**Fix** (owner files: `src/store/MandaratContext.tsx`, `src/lib/syncEnvelope.ts`, `tests/syncEnvelope.test.js`). Stamp at persist time instead of at commit time, as V2-F handoff 1c describes:
1. In `MandaratContext`, `commit` no longer calls `stampCommit` for `how === 'stamp'`. It keeps a ref `stampedDoc` (the doc that `metaRef` was last stamped against). Add `flushStamp()`:

   ```ts
   const flushStamp = () => {
     if (metaRef.current && stampedDoc.current !== latest.current) {
       metaRef.current = stampLocal(stampedDoc.current, latest.current, metaRef.current, Date.now());
     }
     stampedDoc.current = latest.current;
   };
   ```

   - `'epoch'` and `'none'` commits call `flushStamp()` first, then apply as today, and set `stampedDoc.current = next`.
2. Call `flushStamp()` in three places:
   - at the start of `persist(d)`, before `serializeStored`;
   - in `makeSyncPort`'s `meta()`, `replica()`, `applyRemote()` and `adopt()` paths (`src/lib/syncEnvelope.ts:130`), through a new `SyncPortHost.flush()` hook, so the engine never reads an unstamped meta;
   - before a snapshot and before a backup export, if either reads meta.

   A diff over several commits produces one stamp for the net change. This is correct: `reattribute` works on the net `from`→`to`, and paths that changed back to their original value produce no change.
3. Optional, for the storage bloat: do not create a meta until sync is first enabled. In `MandaratContext.tsx:343`, call `makeMeta()` only when the stored `_sync` exists. Otherwise create it in the port's enable path, which already runs `epochReset` (stamping the whole doc) when the choice is made. This removes the clock from never-sync installs.
4. Tests: the eager-form assertions noted in V3-E §5 ("the commit tests pin the current eager form") move to "stamped by the next persist or port read". Add a benchmark guard to `tests/syncEnvelope.test.js`: 50 `checkToday` commits on `heavyDoc()` without a persist must have a median commit cost under 1 ms in Node.

### 4. P2 — LangBoot's AsyncStorage read is serial after the fonts, not parallel

**Where**: `App.tsx:83-90`, `src/i18n/react.tsx:45-58`.

**Evidence.** `App` returns `<Splash />` until `useFonts(FONT_FILES)` resolves. `LangBoot` is mounted only after that, and only then calls `readLangPref()` in its effect. The launch is therefore fonts → language read → (MandaratProvider) doc read: three serial stages, where the plan asks for the language read to run in parallel with the fonts. The added delay is one AsyncStorage round trip, a few ms to tens of ms on a cold launch. `crash.init()` is already started at module load (`App.tsx:20`) and is fine.

**Fix** (owner file: `src/i18n/react.tsx`). Start the read when the module loads, and await the same promise in `LangBoot`:

```ts
// 앱을 여는 순간 읽기 시작한다 — 서체를 불러오는 동안 같이 돈다
let prefRead: Promise<LangPref | null> | null = null;
export function prefetchLangPref() { return (prefRead ??= readLangPref()); }
```

- In `LangBoot`'s effect, call `prefetchLangPref().then(…)`.
- In `App.tsx`, call `prefetchLangPref()` next to `crash.init()` at line 20.

Use the actual return type of `readLangPref`.

### 6. P2 — Heavy pull time on the JS thread

**Where**: `src/lib/syncEngine.ts:474-504` (`cycle`), `src/lib/syncMerge.ts:242` and `:272`.

**Evidence** (`/tmp/r8/perf.js`, same heavy doc; the replica file is 1150 KB):

```
merge(A, B) heavy                            median 159.20 ms  p90 192.58 ms
materialize(merged.doc)                      median   5.62 ms
encodeReplica (push, heavy)                  median  22.83 ms
decodeReplica (pull, heavy)                  median  31.21 ms
pull total: decode x2 + merge + materialize  median 243.23 ms  p90 323.39 ms
```

This is within V2-F's 600 ms Node guard. V4-A's device target is "under about 0.5 s on an older iPhone", and with Hermes's interpretation overhead the pull will likely exceed it.

Mitigation already present, and verified: `readRemotes` skips files whose `modified` time is unchanged (`syncEngine.ts:132`), so the heavy merge runs only when another device wrote. The push path skips identical content.

**Fix.** Keep it as the V4-A device-QA item. If the device measurement shows more than 0.5 s, the owner file is `src/lib/syncEngine.ts`:
- yield between decode and merge (`await new Promise((r) => setTimeout(r, 0))`) so that a tap in between is handled;
- run the merge inside `InteractionManager.runAfterInteractions`.

Finding 3 (fewer clock keys for never-sync installs) does not change this. The merged replica is bounded by the doc.

- **ReminderSync**: 1.5 s debounce, with a skip on `status|planKey` (`ReminderSync.tsx:26-27`). `planReminders` and `planKey` cost 2.1–3.1 ms median.
- **ICloudSync**: 5 s debounce (`PUSH_DEBOUNCE_MS`). It does nothing while sync is off, and the engine skips identical pushes and unchanged remote files.
- Text inputs commit on idle, not per keystroke, so none of the hosts runs per keystroke.

**Print fonts cached once**
- `printFonts.native.ts:7` and `:24-33` keep a single module-level promise, reset only on failure so that the next print retries.
- Memory cost: Medium 1,584,068 B and Bold 1,576,660 B, about 4.2 MB of base64 retained after the first print. This is acceptable for a print-only path and is noted for device QA.
