## F1 — P1: a chart restored from a 저장본 or an older backup after a close can never be closed again

**Where**
- `src/lib/archive.ts:122`: `if (past.some((a) => a.id === archive.id || …)) return null;`
- `src/lib/archive.ts:20-23`: `chartRange` falls back to `firstLogDay(dayLog)` when `chartStart` is missing.
- The paths that create this state:
  - `src/store/MandaratContext.tsx:791-797` (`readSnapshot` puts the **current** archives back on an older doc), used by `Settings.tsx:247`;
  - `src/overlays/BackupImport.tsx:130` (`unionArchives` keeps the current archives over an older backup's doc).

**Mechanism**
1. The archive id is deterministic: `'y' + from`.
2. Close the chart. Then restore a 저장본 from before the close (7 days are kept, so this is easy right after a year close), or import an older backup.
3. The live doc gets back the old `chartStart`, or, from a v3 backup, no `chartStart` at all, so `from` becomes the first log day. The archive of that same chart is still present.
4. Every later `startNewChart` computes the same id and returns `null`. `YearClose` then shows `m.year.sameDay` (YearClose.tsx:106/327), which is wrong, and the user has no way out.
5. If the first log day differs from the archived `from`, the close succeeds instead, but the new archive spans the whole history again: two overlapping archives of the same year.

**Reproduction:** `node probes/p1-stuck-close.js`

```
closed ok: true archives: [ 'y20260101' ]
(a) snapshot restore -> close on Tue Dec 29 2026 => REFUSED | range {"from":"2026-01-01","to":"2026-12-29"} id y20260101
(a) snapshot restore -> close on Fri Jan 15 2027 => REFUSED | range {"from":"2026-01-01","to":"2027-01-15"} id y20260101
(b) v3 import chartStart: undefined | from = 2026-01-01 => close REFUSED
```

With the first log on 01-02 instead, case (b) closes, as the first run showed: `y20260102` overlaps the existing `y20260101`.

**Fix (`src/lib/archive.ts`, with tests in `tests/archive.test.js`)**

1. In `chartRange`, never start before the end of the latest archive when `chartStart` is unknown. Widen the `Pick` to include `archives`, and update the callers' types:
   ```ts
   export function chartRange(doc: Pick<MandaratDoc, 'chartStart' | 'dayLog' | 'archives'>, now: Date) {
     const to = ymd(now);
     const lastTo = (doc.archives ?? []).reduce((m, a) => (a.to > m ? a.to : m), '');
     let from = doc.chartStart ?? firstLogDay(doc.dayLog) ?? to;
     if (!doc.chartStart && lastTo && from < lastTo) from = lastTo;
     return { from: from <= to ? from : to, to };
   }
   ```
2. In `startNewChart`, an existing archive with the same id **and an earlier `to`** is the same chart closed earlier. Replace it with the longer one, keeping its note when the new note is empty. Refuse only a second close on the same day:
   ```ts
   const same = past.find((a) => a.id === archive.id);
   if ((same && same.to === today) || past.some((a) => archive.from === today && a.to === today)) return null;
   const next = same?.note && !archive.note ? { ...archive, note: same.note } : archive;
   // …
   archives: sortCap([...past.filter((a) => a.id !== archive.id), next]),
   ```
   This is safe for iCloud: `ar/<id>` is one LWW register, and the later close wins on every device.
3. Tests to add:
   - restore a pre-close snapshot, then close later: the close succeeds and there is one archive `y…` with the later `to`;
   - import a v3 backup when archives exist: `chartRange.from` is at or after the last `to`.

## F2 — P1: reset, then undo, still wipes another device's unsynced edits

**Where**
- `src/store/MandaratContext.tsx:709-712`: `resetAll` runs `update(…, 'epoch')`.
- The undo goes through `useSnapshotUndo` → `replaceDoc` (`MandaratContext.tsx:754`), which commits with `'stamp'`. The new epoch stays.
- The push debounce is `PUSH_DEBOUNCE_MS = 5000` (`syncEngine.ts:25`, `ICloudSync.tsx`). The undo toast stays 8 s (`Snackbar.tsx:37`), and indefinitely with VoiceOver on. So the reset epoch is normally pushed while the undo is still on screen.

**Mechanism**
1. Device B wrote something that is not yet synced.
2. Device A taps reset and then undo within seconds. A's doc is back, but A's meta now has `epoch = E2`, and every value carries a stamp above E2.
3. When B pulls A, every B value stamped at or below E2 is treated as erased by the reset. B's unsynced edit disappears from B's live doc.
4. The edit survives only in B's `keepCopy` 저장본, which B's user has no reason to open, because nobody reset anything from their point of view.

The existing test `reset and its undo …` (`syncEnvelope.test.js:450`) covers only edits made **after** the reset.

**Reproduction:** `node probes/p2-reset-undo.js`

```
A after undo — goal: goal | epoch: 0mvc62oyo008wet
B reflection after pulling A: null
```

**Fix**
1. In `MandaratContext.tsx`, `resetAll` saves `resetUndo.current = { meta: <meta before the reset>, pushed: <meta.pushed at reset> }`.
2. Add an action `undoReset(snapshot)`. When the revision is unchanged **and** `metaRef.current.pushed === resetUndo.pushed` (the reset epoch was never pushed), it restores the saved meta and commits the snapshot with `'none'`, so A is exactly as before. Otherwise it falls back to today's `replaceDoc`.
3. `Settings.tsx` `doReset` uses this undo instead of the generic `offerUndo`.
4. In `ICloudSync.tsx`, when `meta.epoch` has changed since the last push, debounce the push to at least the toast time (for example 10 s) instead of 5 s.
5. Background pushes during the window are acceptable: the toast is gone once the app leaves.
6. Test to add in `tests/syncEnvelope.test.js`: B's edit before A's "reset + undo" survives when A pulls and B pulls.

## F3 — P1: widget checks are dropped when the app opens on a later day

**Where**
- `src/lib/widgetOps.ts:96`: `x:` ops with `op.day !== tk` return `null`.
- `widgetOps.ts:104-109`: for any day but today, only `habit` survives.
- The widget renders the tap optimistically (`TodayWidget.ios.tsx:129-137`: the item flips to done and `done + 1`). JS does not run while the app is suspended, so ops are applied only the next time the app comes to the foreground.

**Mechanism**
1. A widget-first user checks off a once item, a count item or a hand-added task at 21:00.
2. They open the app the next morning. The check is discarded, and the item is undone again: a "once" item that was done is no longer done.
3. The plan wrote this rule, and V2-C QA line 107 expects it ("the once item is not checked (stale)"). From the data side it is still a silent loss of a user action the UI confirmed.

**Reproduction:** `node probes/p5-widget-stale.js`

```
read same day : [{"kind":"checkToday","ti":0,"ai":0},{"kind":"checkToday","ti":0,"ai":1},{"kind":"checkToday","ti":0,"ai":2},{"kind":"toggleExtra","id":"abc"}]
read next day : [{"kind":"toggleHabitOn","ti":0,"ai":2,"day":"2026-10-17"}]
```

**Fix (`src/lib/widgetOps.ts`, `tests/widgetOps.test.js`, and the V2-C QA line)**

For an op with `op.day < tk`, within the 7-day window Siri already uses:
- **once:** emit `checkToday` when `!!a.done !== op.on`. `done` is not tied to a day; only its log lands on today, which is better than losing it.
- **extra (`x:<id>`):** emit `toggleExtra` when the extra is still in `todayExtra` and `x.done !== op.on`. An undone extra carries over at rollover.
- **count:** emit `checkToday` only for `op.on === true` and when today's count has not already moved. Recording it on `op.day` would need a store action `addCountOn(ti, ai, delta, day)`. That is the cleaner option if the lead accepts a store API addition.

If the owner keeps the drop rule, the widget must stop rendering stale taps as done. That is a `TodayWidget.ios.tsx` change: ignore the press when `day` is not the entry's date. The behaviour must also be stated in the store-facing copy.

## F4 — P1: a stale device leaks a push while the stale-ask is being prepared

**Where:** `src/lib/syncEngine.ts:603-605` (`background`). It checks `enabled`, `block`, `verified` and `phase !== 'needsChoice'`, but not `isStale`.

**Mechanism**
1. `cycle()` sees `isStale(meta)` (`syncEngine.ts:481`) and calls `decide(null)`, which waits on `account()`, `watch()` (up to 10 s of gather) and `readRemotes(all)`. The phase during that time is `'checking'`.
2. If the app goes to the background in that window (the user opens the app, glances at it and leaves), `background()` pushes the stale replica.
3. Other devices merge it. Element paths that were deleted on them more than 180 days ago have lost their tombstones to `gc`, so the stale values come back. Preventing exactly this is why `isStale` forces the ask (V2-F, V4-A).

**Reproduction:** `node --test probes/p3-stale-push.test.js`. It uses the real `createSyncEngine`, `makeSyncPort` and `stampCommit` on the fake iCloud from `tests/syncEngine.test.js`.

```
# phase while preparing the ask: checking
# B pushed while stale (writes before/after): 2 3
# phase after: needsChoice
# pass 1
```

**Fix (`src/lib/syncEngine.ts`):**

```ts
background: async () => {
  const meta = port.meta();
  if (disposed || !meta?.enabled || block || !verified || status.phase === 'needsChoice' || isStale(meta, io.now())) return;
```

`pulledAt` is only refreshed by `pull`/`apply`, so `isStale` stays true until the user has chosen. Add the probe above, inverted, to `tests/syncEngine.test.js`.

## F5 — P2: a failed `readOps` erases pending widget and Siri ops; the ops buffer is capped at 50

**Where**
- `src/widgets/bridge.ios.ts:28-33` catches and returns `[]`.
- `src/hosts/WidgetSync.tsx:61-77` then writes the timeline whenever the signature changed. `updateTimeline` replaces the stored array, so every op that could not be read is gone.
- Separately, `TodayWidget.ios.tsx:136` keeps `ops.concat([op]).slice(-50)`. Past-day habit ops beyond 50 taps without opening the app are lost: 5 habits a day is 10 days.

**Evidence:** code reading. The failure needs the native `getTimeline` to throw (a decode error or an App Group read race), which Node cannot reproduce.

**Fix**
1. In `bridge.ios.ts`, `readOps` returns `null` on error. The `WidgetBridge` type in `src/lib/contracts.ts` (lead) becomes `readOps(): Promise<WidgetOp[] | null>`, and `bridge.ts` follows.
2. In `WidgetSync.tsx`, `if (ops === null) return;`, so nothing is written this round. Then retry on the next doc change or foreground.
3. Raise the cap to about 300 in `TodayWidget.ios.tsx`. The ops are small (about 80 B), so 300 is about 24 KB in the App Group.

## F8 — P2 (tests): the merge fuzz at 50,000 seeds

The plan asks for the sync merge fuzz to be rerun with 50,000 seeds. A scaled copy of `tests/syncMerge.test.js` was run with only the loop bounds replaced by environment variables (`fuzz/syncMerge.scaled.test.js`), in four parallel shards.

| Test | Scale | Result |
|---|---|---|
| `joinStates` commutative, associative, idempotent | 50,000 random triples (from 100 multi-device worlds) | **pass** (365 s) |
| `merge` on documents, the same laws where nothing was clipped | 5,000 triples | **pass** |
| never loses an edit | 50,000 histories (seeds 1–50,000, 2–4 devices) | unmodified oracle fails. Categorised: 242 orphan `x/<id>/done` (by design); with 2 convergence rounds, 327 entries (not-converged markers and their missing paths, all from unconverged worlds); with 6 rounds, 0. **0 real losses** |
| counters are conserved | 50,000 histories | 49,977 exact; 12 clipped but still exact; 11 mismatches, **all** after a below-zero clip; **0** mismatches without a clip |

**Unmodified oracle:** every shard stopped on its first failure. In the first two classes below, the first failing seeds were 509, 12530, 25418 and 38096 (the paths `x/zz/done`, `x/k1/done` and `x/zzd2/done`), and 1009, 17743, 26367 and 37945 (counts).

**Categorised rerun (`fuzz/ctr.test.js`):** every failure is recorded instead of asserted, and classified:

1. **`x/<id>/done` without its element `x/<id>`.**
   - Seed 509: a reset (epoch E) on one device removed the today extra `zz`. Another device that had not seen the reset toggled `done` on it later.
   - The `done` register keeps the later stamp, but its head `x/zz` is erased, so `assemble` drops the item.
   - This is the V1-F register table ("`x/<id>/done` — element; ignored without `x/<id>`"): delete-wins for a sub-register. It is not a loss in the app's terms, and the day's `d/<day>/<ti>-x<id>` record survives.
2. **Counters that went below zero through concurrent decrements**, then were clipped by `assemble`/`migrate` and later re-based by local stamps. This is the case V2-F §7.2 and the test comment already exclude ("함께 줄여 0 밑으로 간 수"). The instrumented copy checks after every merge whether the document count differs from the joined `b + Σp`. All failing counter seeds hit such a clip; none failed without one.
3. **Worlds that are not converged after the test's `converge()`.**
   - With the test's 2 hub rounds, a few worlds stay unconverged, and their late `d/<day>/<key>` stamps are missing on the hub (first example: seed 1203).
   - The cause is the harness: `pull` randomly runs `materialize` and stamps on the puller after the hub's last round, and those stamps never travel back.
   - Rerun of all 50,000 seeds with 6 rounds (`fuzz/dbg2.test.js`, `ROUNDS=6`): **0** unconverged worlds and **0** losses outside class 1.
4. **Any other loss:** none, also checked: no stamp at or below the epoch, no invented stamp.

**Fix (`tests/syncMerge.test.js`)**
- In the never-loses oracle, skip `x/<id>/done` when the converged state has no `x/<id>`.
- In `converge()`, repeat the rounds until no replica changes (a fixed point, capped at about 10 rounds) instead of a fixed 2.
- In the counter test, skip a seed whose merged count was clipped at any step, which is the exact condition the comment describes, instead of the `expectCount >= 0` heuristic.
- Then the suite can be run at any seed count. Optionally read a `FUZZ_SEEDS` environment variable, so wave 10 can rerun at scale without editing.

## Verified correct

Each item was checked by a script or by a test at `ddc3d51`, as noted.

- **migrate and backup v4 on real old data.**
  - Docs were built with the **old code** from git history and run through the current `parseBackup`, `migrate` and `openStored`:
    - `34c747d` (v1, raw doc, no schema);
    - `c0699c3` (schema 1, action kinds);
    - `6e0070e` (schema 3, reviews, closedDays, areasSet, lastBackupAt).
  - Every stored field survives, including texts with emoji, kinds, logs, extras, detached `xh` keys and reviews.
  - No v4 field is invented: archives, chartStart, focusStart, reminders and paper all stay absent.
  - `migrate` is idempotent and JSON-stable, `makeBackup → parseBackup` round-trips, the opened store has sync off, and the first close of an upgraded chart starts at the first log day. `node probes/p4-old-backups.js $SCRATCH` printed `ok` for all three.
  - Schema 5 is rejected (`newer`), and `summary.archives` is present (`tests/backup.test.js`).
- **Archive slicing.** `makeArchive` cuts dayLog, dayMeta and closedDays to `[from, to]` and reviews to `[from − 6, to]`, the same window as `cleanArchive`. Cell keys stay `ti-ai` inside the archive. `focusMinutes − focusStart` is never below 0. `makeArchive` is a fixed point of `cleanArchives`.
- **`startNewChart` undo.** The snapshot is taken with `getDoc()` before the close (`YearClose.tsx:101`). The undo restores it through `replaceDoc` only when the revision is unchanged. With sync, the undo tombstones `ar/<id>`, so the archive does not come back from other devices, and `cs`/`fs` are restamped. `applyRemote` bumps the revision only when the doc changed, so a stale undo is refused, not applied over merged data.
- **Snapshots and archives.** Snapshots are written without archives or `_sync` (`docOnlyJson`). `readSnapshot` puts the current archives back. `keepCopy` force-writes today's snapshot through the same `snapChain`, so a late daily snapshot cannot overwrite it. See F1 for the one interplay gap.
- **Archives survive every path.**
  - `resetAll` uses `resetDoc` (settings and archives) with an epoch that restamps them;
  - backup import uses `unionArchives`;
  - `adopt` unions;
  - `mine` unions, then runs the epoch reset;
  - a higher-epoch pull re-adds archives the remote never deleted after its epoch (`applyPulled`);
  - same-epoch merge works per `ar/<id>` register.
  - Covered by `syncEngine.test.js:256, 279, 440, 463` and `syncEnvelope.test.js:545`, which all pass.
- **Merge laws.** These hold at 50,000 and 5,000 triples (F8). Every oracle failure at scale is one of the two documented semantics.
- **Join-at-apply.** `applyRemote` reads `host.doc()` and `host.meta()` inside its own body and awaits nothing. `pull` awaits only `keepCopy` and then applies synchronously. The race tests pass (`syncEnvelope.test.js:151, 395`; `syncEngine.test.js:337`).
- **Re-key on a cloned meta.** `boot` re-keys before the first push. Pushes and `background` are blocked until `verified`. Counters add up after a clone (`syncEngine.test.js:506`).
  - Residual, not a finding: stamps made between store load and `boot` (the rollover only) carry the cloned tag. It is harmless because the rollover touches no counter.
  - Every fresh iOS meta has `vendor` undefined (`makeMeta` passes no vendor), so first boot always re-keys once. That is harmless.
- **Epoch restamp.** `epochReset` stamps every path of the kept doc above the new epoch (`syncLocal.test.js:226`, `syncEnvelope.test.js:134`).
- **keepCopy.** It runs before every choice and before applying a higher epoch. A choice whose copy cannot be written changes nothing (`syncEngine.test.js:307, 322`; `syncEnvelope.test.js:493, 508`).
- **newerApp.** A newer-schema replica stops the engine with nothing merged, nothing pushed and `seen` unchanged (`syncEngine.test.js:478`). `decodeReplica` checks `schema` before anything else.
- **Envelope and older builds.** `migrate` drops `_sync`, so an older build keeps the doc (`syncEnvelope.test.js:81`). A garbage `_sync` loads the doc with sync off. An older build rejects v4 backups. A downgrade would drop archives, but the App Store offers no downgrade, so this is not a finding.
- **Widget read-before-write.** One promise chain does `readOps → planOps → run → writeTimeline`. `planOps` is idempotent on a re-read (`widgetOps.test.js:127`). The remaining gap is F5.
- **Device-local keys.** Reset, import, sample and template never touch `mandarat:{lang,pro,notify,crash,print}:v1`. The only removal in those paths is the editor draft (`dropEditorDraft`), which is intended. Checked by grepping every `AsyncStorage` write and removal in `src/`.
- **Store commit races.** `latest` and `metaRef` are updated together in `commit`. `persist` always writes the pair taken from `latest.current`. The background flush runs in a microtask after the other listeners. The midnight rollover commits through `commit` (no revision bump) and re-runs `rolloverToday` after an undo.
