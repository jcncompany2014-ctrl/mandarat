## Findings

### P1-1 — The coordinated read blocks for the whole download, with no time limit

`modules/icloud-sync/ios/ICloudSyncModule.swift:125-126`, `:322-332` (`coordinatedRead`).

**The problem.** Apple's documentation for `NSFileCoordinator.coordinate(readingItemAt:options:error:byAccessor:)` says:

> "If the device has not yet downloaded the file at the given URL, this method blocks (potentially for a long time) while the file is downloaded. If the file cannot be downloaded, this method fails."

`download(_:)` deliberately gives up after `downloadWait` (10 s). When a stale `.downloaded` copy exists, it returns normally so that the stale copy is read (V3-F deviation 4). The coordinated read that follows then waits for the **current** version, with no time limit:

- **On a slow network or in airplane mode:** the "stale-copy fallback" never happens, and `read` hangs instead of returning or rejecting with `E_TIMEOUT`.
- **`io` is serial:** while the read hangs, every later `status`, `write`, `remove` and `deviceKey` call queues behind it. That includes the background push (see P2-5).

**The fix.** Bound the coordinated read with `NSFileCoordinator.cancel()`. Apple's documentation: "You can call this method from any thread … If the block passed to the file coordination call has not yet been executed … the method returns" with `NSUserCancelledError`. If the read is cancelled, fall back to the local copy without coordination. Every write is `.atomic` (a rename), so an uncoordinated read of the local file never sees half a file.

```swift
  /// 조율된 읽기 — 최신본을 받느라 오래 막히면(문서: "blocks, potentially for a long time") limit 뒤에 그만두고
  /// 이 기기에 있는 사본을 그대로 읽는다(쓰기는 모두 .atomic이라 반쯤 쓴 파일은 없다).
  static func coordinatedRead(_ url: URL, limit: TimeInterval = downloadWait) throws -> Data {
    var coordinationError: NSError?
    var result: Result<Data, Error> = .failure(error("E_IO", "Coordinated read did not run"))
    let coordinator = NSFileCoordinator(filePresenter: nil)
    let timer = DispatchWorkItem { coordinator.cancel() }
    DispatchQueue.global(qos: .utility).asyncAfter(deadline: .now() + limit, execute: timer)
    coordinator.coordinate(readingItemAt: url, options: [], error: &coordinationError) { target in
      timer.cancel()
      result = Result { try Data(contentsOf: target) }
    }
    timer.cancel()
    if let coordinationError {
      if coordinationError.domain == NSCocoaErrorDomain, coordinationError.code == NSUserCancelledError {
        // 시간이 다 됐다 — 예전 사본이 있으면 그것을(합치기는 단조라 잃는 것이 없다), 없으면 E_TIMEOUT
        guard let local = try? Data(contentsOf: url) else {
          throw error("E_TIMEOUT", "Download did not finish in \(Int(limit)) s")
        }
        return local
      }
      throw mapped(coordinationError)
    }
    return try result.get()
  }
```

The call site at `:126` stays the same. `download(_:)` has already spent up to 10 s, so the total stays within about 20 s.

To bring the total back to 10 s, pass the remaining time instead. Make `download` return its deadline (`static func download(_ url: URL) throws -> Date`), then call:

```swift
let deadline = try ICloudSyncModule.download(url)
var out = [try ICloudSyncModule.inflate(try ICloudSyncModule.coordinatedRead(url, limit: max(1, deadline.timeIntervalSinceNow)))]
```

**Device QA.** Add this to the V3-F "Download wait" item: in airplane mode, with a stale copy on the device, `read` returns the stale replica within about 10 to 20 s. Without any copy, it rejects with `E_TIMEOUT`. In neither case does it hang, and a `write` issued straight afterwards completes.

### P1-2 — The cached container URL outlives a sign-out

`modules/icloud-sync/ios/ICloudSyncModule.swift:186-195` (`resolveContainer`).

**The problem.** The cached URL is returned (`:188`) **before** the identity token is checked (`:189`). `NSUbiquityIdentityDidChange` is only delivered when the app is running, and it is posted asynchronously; the handler then hops to `io`. Between the sign-out and that hop, `fileURL()` keeps returning the old container. The effects differ by call:

- `write` and `remove` fail with a generic `E_IO` instead of `E_NO_ACCOUNT`, so V4-A maps them to "skip this file" rather than to `noAccount`.
- `start()` reports `true`.

`currentStatus()` checks the token first and is correct, so the module disagrees with itself.

**The fix.** Check the token on every call. `ubiquityIdentityToken` is cheap; Apple's documentation says it may be called from the main thread, unlike `url(forUbiquityContainerIdentifier:)`. Drop the cache when the token is gone:

```swift
  private func resolveContainer() -> URL? {
    dispatchPrecondition(condition: .onQueue(io))
    guard FileManager.default.ubiquityIdentityToken != nil else {
      containerURL = nil
      return nil
    }
    if let url = containerURL { return url }
    guard let url = FileManager.default.url(forUbiquityContainerIdentifier: ICloudSyncModule.containerId) else {
      return nil
    }
    containerURL = url
    return url
  }
```

The tests in `tests/icloudModule.test.js` still hold: there is still exactly one `url(forUbiquityContainerIdentifier:)` call, and it still sits after the precondition.

### P2-1 — pro-store: the `Transaction.updates` task captures a non-`Sendable` `self` in a `@Sendable` closure

`modules/pro-store/ios/ProStoreModule.swift:26-34`.

**The problem.**
- `Task.detached` takes a `@Sendable` closure, and `ProStoreModule` (a `BaseModule` subclass) is not `Sendable`. In Swift 5.9 mode this gives no diagnostic or only a warning. In Swift 6 mode it is an error ("capture of 'self' with non-sendable type in a `@Sendable` closure").
- When `self` is gone, the loop keeps running, because `self?.sendEvent` just no-ops. `OnDestroy` (called from `ModuleHolder.deinit`, `Core/ModuleHolder.swift:144`) does cancel the task, so this is not a leak today. A `guard` is still the cheaper safety net.

**The fix.** It is Swift 6-proof, because the task no longer captures `self`, and it stops on its own. It hands events to a `Sendable` sink:

```swift
    OnCreate {
      let emit: @Sendable (String, Bool) -> Void = { [weak self] id, owned in
        self?.sendEvent("onEntitlementChange", ["id": id, "owned": owned])
      }
      self.updates = Task.detached {
        for await result in Transaction.updates {
          if Task.isCancelled { return }
          guard case .verified(let transaction) = result else { continue }
          await transaction.finish()
          emit(transaction.productID, await ProStoreModule.isOwned(transaction.productID))
        }
      }
    }
```

In Swift 6 mode the `emit` closure would still need `ProStoreModule: @unchecked Sendable`. That is safe here: the only mutable state is `updates`, which is written only in `OnCreate` and `OnDestroy`. Writing `public class ProStoreModule: Module, @unchecked Sendable` is enough. It is not needed while the pod stays on 5.9.

### P2-2 — pro-store: run the scene lookup and the purchase in one main-actor hop

`modules/pro-store/ios/ProStoreModule.swift:61-65`.

**Why it compiles today.** The iOS 17 declaration is:

```swift
@MainActor func purchase(confirmIn scene: some UIScene, options: Set<Product.PurchaseOption> = []) async throws -> Product.PurchaseResult
```

`purchase(options:)` is also `@MainActor`. `UIWindowScene` is a `@MainActor` class and therefore implicitly `Sendable`, so handing it from `activeScene()` back to a main-actor method is legal. It compiles and is correct.

**Why change it anyway.** There are two hops. Between them, the scene can change state, for example when the iPad window is dismissed. A single main-actor helper is tidier and makes the iOS 17 branch obvious:

```swift
  @MainActor
  static func buy(_ product: Product) async throws -> Product.PurchaseResult {
    if #available(iOS 17.0, *), let scene = activeScene() {
      return try await product.purchase(confirmIn: scene)
    }
    return try await product.purchase()
  }
```

At the call site:

```swift
      do {
        result = try await ProStoreModule.buy(product)
      } catch {
        throw ProStoreModule.mapped(error)
      }
```

`tests/pro.test.js` greps for `purchase(confirmIn:` and `#available(iOS 17.0, *)`. Both remain.

### P2-3 — icloud-sync: drop the `main.sync` in `BackgroundTask`

`modules/icloud-sync/ios/ICloudSyncModule.swift:429-457`.

**Why it can go.** Apple's documentation now declares both calls `nonisolated` and says each "can be safely called on a non-main thread":

```swift
nonisolated func beginBackgroundTask(withName taskName: String?, expirationHandler handler: (@MainActor @Sendable () -> Void)? = nil) -> UIBackgroundTaskIdentifier
nonisolated func endBackgroundTask(_ identifier: UIBackgroundTaskIdentifier)
```

**Is the current code correct?**
- **Deadlock:** no. Nothing on main ever waits for `io`. I checked `OnDestroy` (`main.async`), the `stop` and `list` functions (`runOnQueue(.main)`), and Expo's JS thread, which never blocks on `io`.
- **`MainActor.assumeIsolated`:** it is back-deployed to iOS 13 (`static func assumeIsolated<T>(_ operation: @MainActor () throws -> T, …) rethrows -> T where T : Sendable`), so 16.4 is fine.

The `main.sync` is still the one place where `io` can stall behind a busy main thread. The only remaining main-actor member is `UIApplication.shared`, which in Swift 5 mode is a warning, not an error.

**The simpler form.** The lock is needed because the expiration handler (main) and `end()` (`io`) can race:

```swift
final class BackgroundTask: @unchecked Sendable {
  private let lock = NSLock()
  private var id: UIBackgroundTaskIdentifier = .invalid

  static func begin(_ name: String) -> BackgroundTask {
    let task = BackgroundTask()
    // beginBackgroundTask는 nonisolated — io 줄에서 바로 부른다. `shared` 접근은 Swift 5 모드에서 경고뿐이다
    let id = UIApplication.shared.beginBackgroundTask(withName: name) { task.end() }
    task.lock.withLock { task.id = id }
    return task
  }

  func end() {
    let id: UIBackgroundTaskIdentifier = lock.withLock { defer { self.id = .invalid }; return self.id }
    guard id != .invalid else { return }
    UIApplication.shared.endBackgroundTask(id)   // nonisolated, any thread
  }
}
```

This is optional. If you keep the current form, it is correct.

### P2-4 — icloud-sync: the metadata query is not restarted after an account change

`modules/icloud-sync/ios/ICloudSyncModule.swift:65-74`.

**The problem.** On `NSUbiquityIdentityDidChange`, the container cache is dropped, but the running `NSMetadataQuery` is left in place. It keeps the old account's results, or empty results, until JS calls `stop()` then `start()`.

**The fix.** Either document in V4-A that `accountChanged` must `stop()` then `start()`, or stop the query natively:

```swift
        self.io.async {
          self.containerURL = nil
          let status = self.currentStatus()
          DispatchQueue.main.async { self.stopQuery() }   // 새 계정이면 JS가 start()로 다시 연다
          self.sendEvent("onAccountChange", ["available": status.available, "account": status.account])
        }
```

### P2-5 — icloud-sync: a push queued behind a long read has no background task yet

`modules/icloud-sync/ios/ICloudSyncModule.swift:143-154`.

**The problem.** `BackgroundTask.begin` runs only when the `write` block reaches the front of the serial `io` queue. If the app goes to the background while a `read` is still waiting for its download (up to 10 s, or unbounded before P1-1), the queued push has no task protecting it. The app can be suspended before the push starts.

**The fix.** Cover the whole `io` backlog when the app enters the background. `OnAppEntersBackground` exists in SDK 56 (`Api/Factories/EventListenersFactories.swift:39`). `io` is serial, so the `end` runs after everything already queued:

```swift
    OnAppEntersBackground {
      let task = BackgroundTask.begin("icloud-sync drain")
      self.io.async { task.end() }
    }
```

A push that JS issues after this point still opens its own task, so `defer { task.end() }` stays.

### P2-6 — icloud-sync: conflict versions are listed outside the coordinated read

`modules/icloud-sync/ios/ICloudSyncModule.swift:127`.

**The problem.** `NSFileVersion.unresolvedConflictVersionsOfItem(at:)` is called after the coordinated read has returned. A version that arrives in between is read here but not by the coordinated read. This is harmless, because the join is monotone and V3-F deviation 1 already reasons about it. Taking the list inside the reader block makes "what was read" and "what is resolved" the same snapshot.

**The fix.** Return `(Data, [NSFileVersion])` from `coordinatedRead`, and inside the accessor call:

```swift
NSFileVersion.unresolvedConflictVersionsOfItem(at: target) ?? []
```

### P2-7 — icloud-sync: `inflate` has no size limit

`modules/icloud-sync/ios/ICloudSyncModule.swift:369-379`.

**The problem.** `NSData.decompressed(using: .zlib)` (iOS 13+, raw DEFLATE) allocates the whole output. The only files read are our own replicas, which are under `SIZE_WARN`, so this is not a security issue. A corrupt or very large file would still allocate without bound on `io`.

**The fix.** Reject inputs whose compressed size is far above the expected maximum before inflating, for example:

```swift
guard data.count < 8 << 20 else { throw error("E_CORRUPT", "Replica too large") }
```

Memory today is about 3× the JSON at the peak (String → `Data` → compressed `NSData` → `Data`). That is fine for the 2 MB QA case.

### P2-8 — App Intents: which `AppShortcut` initializer is used, and the fallback if Xcode objects

`native/ios/AppIntents.swift:112-135`.

Apple's documentation JSON has two overloads with the same labels:

| Overload | iOS availability |
|---|---|
| `init<Intent>(intent: Intent, phrases: [AppShortcutPhrase<Intent>], shortTitle: LocalizedStringResource? = nil, systemImageName: String? = nil)` | **16.0**, deprecated 17.0 |
| `init<Intent>(intent: Intent, phrases: [AppShortcutPhrase<Intent>], shortTitle: LocalizedStringResource, systemImageName: String)` | **17.0** |

**What happens at a 16.4 deployment target.** The solver ranks a declaration that is potentially unavailable at the deployment target below an available one (`SK_Unavailable`), so the 16.0 overload is chosen.
- There is no deprecation warning, because it is deprecated only from 17.0, above the deployment target.
- At runtime on iOS 17 and later, the 16.0 overload remains valid.

This is the same split SDK pattern that Apple's iOS 16 samples compile against.

**If the EAS build instead reports "'init(intent:phrases:shortTitle:systemImageName:)' is only available in iOS 17.0 or newer"**, force the 16.0 overload with optional arguments. The App Intents metadata extractor accepts these, because they are still literals:

```swift
    AppShortcut(
      intent: ShowTodayIntent(),
      phrases: ["Show Today in \(.applicationName)", "Open Today in \(.applicationName)"],
      shortTitle: "shortcut.showToday" as LocalizedStringResource?,
      systemImageName: "checklist" as String?
    )
```

Apply the same change to the other three shortcuts.

### P2-9 — Widget ops: the read-modify-write across processes is not atomic

`native/ios/TodayStore.swift:248-272`.

**The problem.** `appendOp` re-reads just before it writes, which narrows the window. It does not close it: the widget extension's `WidgetsAppIntent` (`expo-widgets/ios/Widgets/AppIntent.swift:79-88`) does the same read, merge and `set` on the same key, in another process. V3-B device QA 9 already covers this, and the race is a sub-millisecond window, so no change is required.

**If QA 9 ever loses a check,** serialize with a file lock in the App Group container. Use `NSFileCoordinator` on a sentinel file in `FileManager.containerURL(forSecurityApplicationGroupIdentifier:)`; it works across processes. Note that expo-widgets' own write would not take that lock, so this fixes only Siri against Siri.

## Verified as correct

### pro-store (`ProStoreModule.swift`)

**API availability.** Every StoreKit 2 API used is available at the 16.4 deployment target.

| API | iOS availability |
|---|---|
| `AppStore.canMakePayments` | 15.0 (`static var`, nonisolated, safe in a sync `Function`) |
| `Product.products(for:)` | 15.0 |
| `Transaction.updates` and `Transaction.currentEntitlements` | 15.0 (not deprecated; only `currentEntitlement(for:)` is, in 18.4) |
| `AppStore.sync()` | 15.0 |
| `Transaction.finish()` and `revocationDate` | 15.0 |
| `purchase(confirmIn: some UIScene, options:)` | 17.0 and `@MainActor`, correctly behind `#available(iOS 17.0, *)` |
| `purchase(confirmIn: UIViewController, …)` | 18.2, not used |

**Language checks.** These are all valid Swift:
- `if #available(...), let scene = await ...` (an availability check combined with an optional binding in one condition);
- `case .success(.unverified(_, _))`;
- `@unknown default` on `Product.PurchaseResult`;
- `case .networkError:` without binding its `URLError`.

**Expo DSL overloads.**
- The async closures resolve to the concurrent `AsyncFunction` (`sending @escaping @Sendable (A0, repeat each A) async throws -> sending R`, `ConcurrentFunctionFactories.swift:21`).
- None of these closures captures `self`; they call only static helpers. That makes them valid `@Sendable` closures even in Swift 6 mode.
- `@_inheritActorContext` inherits a nonisolated context, because `AnyModule.definition()` is not actor-isolated. The bodies run on the global executor, not on main.
- `Function("canPay")` resolves to the sync overload.

**Record.** `ProProductRecord` has all of its `@Field`s defaulted, so the synthesized `init()` satisfies `Record`. `Field` is a `final class … @unchecked Sendable` (`Core/Records/Field.swift:6`).

**Error mapping to JS.**
- `Exception(name:description:code:)` exists (`Exception.swift:32`).
- `ConcurrentFunctionDefinition.call` wraps a thrown `Exception` in `FunctionCallException`. Its `code` returns the cause's code (`AnyFunctionDefinition.swift:44-49`), so JS sees `E_NETWORK`, `E_NOT_ALLOWED`, `E_UNAVAILABLE`, `E_CANCELLED` or `E_UNKNOWN` unchanged.
- `Exception` conforms to `JavaScriptThrowable`, which carries `code` into the JS error.
- `mapped()` passes an `Exception` through, and covers `StoreKitError` (a `default` catches the iOS 18.4 `.unsupported` case), `Product.PurchaseError` and `NSURLErrorDomain`.
- The `error` parameter shadowing the static `error(_:_:)` is handled with `self.error`. In `load`, the bare `error(...)` call is outside the `catch`, so it resolves to the static method.

**Event lifetime.**
- `OnCreate` runs from `ModuleHolder.init` (`Core/ModuleHolder.swift:50`), at app-context start-up. That is early enough to catch an Ask to Buy approval or a purchase interrupted by a kill.
- `OnDestroy` runs from `ModuleHolder.deinit` and cancels the task.
- `sendEvent` is safe from any thread: `LegacyEventEmitterCompat.sendEvent` schedules onto the JS runtime.

**Purchase flow.**
- Verified transactions are finished, and unverified ones are left open.
- A refund that arrives through `updates` gives `owned: false`, because `currentEntitlements` excludes revoked transactions and the code checks `revocationDate == nil` as well.

**Podspec.** iOS 16.4, Swift 5.9, `StoreKit` and `static_framework` match `expo-haptics`.

### icloud-sync (`ICloudSyncModule.swift`)

**Queues.**
- Every sync `AsyncFunction` with `.runOnQueue(...)` resolves to `AsyncFunctionDefinition`. `ConcurrentFunctionDefinition` has no `runOnQueue`, so the call is unambiguous. `runOnQueue` sets the queue, and the body is run with `queue.async` (`AsyncFunctionDefinition.swift:138-161`).
- `.runOnQueue(.main)` resolves `DispatchQueue.main` through the `DispatchQueue?` parameter.
- `url(forUbiquityContainerIdentifier:)` is called only on `io`, with a `dispatchPrecondition` guarding it. It is never called on main.

**`NSMetadataQuery` on the main run loop.**
- The query is created, started and stopped only on main: `start` uses `main.async`, `stop` and `list` use `runOnQueue(.main)`, and `OnDestroy` uses `main.async`.
- Apple's documentation for `start()`: "must be called from the receiver's operation queue". With no `operationQueue` set, that is the thread that created the query, here main.
- The observers are registered with `queue: .main`.
- `collect` brackets its reads of `results` with `disableUpdates`/`enableUpdates`.

**Hidden Data scope and file naming.**
- `NSMetadataQueryUbiquitousDataScope` is the right scope. Files live at `<container>/Sync/v1/*.jsonz`, outside `Documents`, and `app.json` has no `NSUbiquitousContainers`, so nothing appears in the Files app.
- The predicate `%K LIKE %@` on `NSMetadataItemFSNameKey` is Apple's documented pattern. `collect` then filters on the parent folders and `isValidName`.
- The name regex `^Sync/v1/[0-9a-z]{1,64}\.jsonz$` blocks path traversal before any URL is built.

**File coordination and deadlocks.** There are no nested coordinations: `resolve`'s `.forMerging` write starts after the read has returned. All coordinators use `filePresenter: nil`, so there is no in-process presenter to deadlock against.
- `.forReplacing` is paired with `Data.write(.atomic)`.
- `.forDeleting` treats a missing file as success, via `catch let error as CocoaError where error.code == .fileNoSuchFile`.
- Errors from the accessor block are carried out through `inner` and `Result`.

**The 10 s download wait.**
- `startDownloadingUbiquitousItem` is called only when the item is not `.current`.
- The status is polled every 0.25 s, with `removeAllCachedResourceValues()` on a `var` copy, so values are not cached between polls.
- The deadline is `Date() + 10`.
- After the deadline, `.downloaded` is accepted (the stale-copy rule) and anything else gives `E_TIMEOUT`.
- `URLUbiquitousItemDownloadingStatus?` compared with `.current` compiles.

The only gap is the read that follows the wait (P1-1).

**Background task for pushes.**
- `beginBackgroundTask` wraps the write, its expiration handler ends the task, and `defer` ends it on every exit.
- `end()` is idempotent (the `.invalid` guard), and `id` is only touched on main.
- The expiration-handler type (`@MainActor @Sendable`) is satisfied, because `task` is `@unchecked Sendable`.

**zlib and the file format.** `NSData.compressed`/`decompressed(using: .zlib)` (iOS 13+) produces raw DEFLATE. The `MZ01` magic is checked before inflating, and both directions map their failures to `E_IO` or `E_CORRUPT`.

**Device key.**
- Data is written with `[.atomic, .completeFileProtectionUntilFirstUserAuthentication]`.
- `isExcludedFromBackup` is set on the folder and the file. Both URLs are `var`, as the mutating `setResourceValues` requires.
- There is no `identifierForVendor`.

**Account.**
- The `ubiquityIdentityToken` archive is hashed with SHA-256 (CryptoKit, iOS 13+). Its first 16 hex characters are the fingerprint.
- `.NSUbiquityIdentityDidChange` is the correct Swift name. The observer is removed in `OnDestroy`.
- `sendEvent(_:_ body: [String: Any?])` sends a `nil` `account` to JS as `null`.

**Records and errors.**
- `@Field var account: String? = nil` is supported (see the `Field.swift:57` comment).
- Returning `[ICloudFileRecord]` converts element by element.
- Every thrown error passes through `guarded`/`mapped`, so JS always receives a coded `ICloudSyncError`. `FunctionCallException` forwards the cause's code on the promise path too (`Promise.reject` → `rejecter(exception)`).

**Swift 5.9 compile checks.**
- `guarded<T>` infers `T` from a multi-statement closure (Swift 5.7+).
- The `try` placement in `if try downloadStatus(url) == .current` is valid.
- `onMain`'s non-escaping `@MainActor` closure is captured by the non-escaping `DispatchQueue.main.sync` closure, which is allowed.
- `MainActor.assumeIsolated` is back-deployed (iOS 13).
- The `@Sendable` parameter of `NotificationCenter.addObserver(…using:)` produces at most a warning in Swift 5 mode for the non-`Sendable` `handler`. It would be an error only in Swift 6 mode, which these pods do not use.

### App Intents and TodayStore (`native/ios`)

**Compilation into the app target.**
- Inline modules compile these files into the main target only.
- `expo-modules-autolinking` classifies a Swift file as a module only if it matches `func definition() -> …ModuleDefinition` (`inlineModules.ts:27`). Neither file does, so no provider entry is generated.

**API availability and constant metadata.** Every App Intents API used is available at iOS 16.4.

- **Intent metadata.**
  - `static let title: LocalizedStringResource` satisfies `static var title { get }`. String-literal keys keep the App Intents metadata constant-extractable.
  - `static let description = IntentDescription("…")` resolves to `init(_ descriptionText: LocalizedStringResource, categoryName: LocalizedStringResource? = nil, searchKeywords: [LocalizedStringResource] = [])`, available from iOS 16.0. Its inferred type is `IntentDescription`, which satisfies the requirement.
  - `static let openAppWhenRun: Bool` is valid. Its iOS 26 deprecation does not warn below a 26.0 target.
- **Dialogs.**
  - `IntentDialog` (iOS 16.0) can be built from a key literal (`"dialog.openAppFirst"`, looked up in `Localizable.strings`).
  - It can also be built from `"\(s)"`, which becomes a `LocalizedStringResource` with key `%@` and argument `s`. That key is absent from the tables, so the formatted argument is shown, which is the intended runtime text.
- **Results.**
  - Both `return` paths in each `some IntentResult & ProvidesDialog` function are `.result(dialog:)`, so the opaque type is the same.
  - The plain `some IntentResult` intents always return `.result()`.
- **`@MainActor perform()`.** Using it on an async protocol requirement is allowed. The two background intents are nonisolated, and `WidgetCenter.reloadTimelines` is safe from there.
- **Shortcuts provider.** `AppShortcutsProvider.appShortcuts` takes its `@AppShortcutsBuilder` from the protocol requirement. Every phrase contains `\(.applicationName)`, and `AppShortcuts.strings` keys use `${applicationName}`.

**TodayStore against expo-widgets.**
- It matches `WidgetsStorage`: the suite `group.com.jcncompany.mandarat` equals the `groupIdentifier` in `app.json`, and the key is `__expo_widgets_TodayWidget_timeline`.
