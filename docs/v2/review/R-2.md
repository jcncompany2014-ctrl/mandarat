### P1

#### R3-1 · The widget extension has no privacy manifest (expect ITMS-91053 on upload) — P1

- **Where:** the prebuild output `ios/ExpoWidgetsTarget/` has no `PrivacyInfo.xcprivacy`. The source is `app.json:48` (`ios.privacyManifests` reaches the main app only) and `node_modules/react-native/scripts/cocoapods/privacy_manifest_utils.rb:52-53`.
- **Evidence:**
  - `privacy_manifest_utils.rb:53`, `get_application_targets`, filters `symbol_type == :application`. Pod-manifest aggregation therefore writes only into `Mandarat/PrivacyInfo.xcprivacy`, never into the app-extension target.
  - The extension calls required-reason APIs:
    - `UserDefaults(suiteName:)` in `node_modules/expo-widgets/ios/WidgetsStorage.swift:3`.
    - The ios `Podfile` target `ExpoWidgetsTarget` runs `use_react_native!`, so React core and ExpoModulesCore are linked into the `.appex`. Both use `stat` / `NSFileModificationDate` and `systemUptime`.
  - `find node_modules/expo-widgets -name 'PrivacyInfo*'` finds nothing, so no pod ships a manifest for the extension either.
  - App Store Connect reports a missing declaration per binary, `PlugIns/ExpoWidgetsTarget.appex/ExpoWidgetsTarget`. Since 2024-05-01 that blocks the upload.
- **Fix** (owner files `plugins/withWidgetStrings.js` and `scripts/prebuild-checks/widgets.js`):
  1. In `withWidgetStrings.js`, the `withDangerousMod` step that already writes `ExpoWidgetsTarget/<lang>.lproj` should also write `ios/ExpoWidgetsTarget/PrivacyInfo.xcprivacy`:
     ```xml
     NSPrivacyTracking false; NSPrivacyTrackingDomains []; NSPrivacyCollectedDataTypes [];
     NSPrivacyAccessedAPITypes:
       NSPrivacyAccessedAPICategoryUserDefaults   → ["1C8F.1", "CA92.1"]
       NSPrivacyAccessedAPICategoryFileTimestamp  → ["C617.1"]
       NSPrivacyAccessedAPICategorySystemBootTime → ["35F9.1"]
     ```
  2. In `addWidgetStrings`, the `withXcodeProject` step that already creates the widget's `PBXResourcesBuildPhase` should add a `PBXFileReference` plus `PBXBuildFile` for `PrivacyInfo.xcprivacy` into that phase. Keep it idempotent, the same way as the `.strings` variant group.
  3. Add a check to `scripts/prebuild-checks/widgets.js`: the file exists, it parses with `ctx.plist`, it declares `1C8F.1`, and its build file is in the widget Resources phase.
  4. Note in `docs/v2/device-tests.md`: read the App Store Connect email after the first TestFlight upload, and add any reason it still names.

### P2

#### R3-2 · `C617.1` and the ubiquity container: no current use needs it, and no code fits a future one — P2 (answer to plan §7's question)

- **Where:** `app.json:58-62` and `modules/icloud-sync/ios/ICloudSyncModule.swift:272-273, 309`.
- **Evidence:**
  - `C617.1` covers metadata of files "inside the app container, app group container, or the app's CloudKit container". The iCloud Documents ubiquity container (`iCloud.com.jcncompany.mandarat`, `CloudDocuments`) is none of those three. So **`C617.1` does not cover ubiquity-container timestamps.**
  - The module does not call an API from the File-timestamp list on the ubiquity container. It reads dates and sizes through `NSMetadataItem` attributes (`NSMetadataItemFSContentChangeDateKey`, `NSMetadataItemFSSizeKey`, lines 272-273). The only `resourceValues` keys it uses are `.isUbiquitousItemKey` and `.ubiquitousItemDownloadingStatusKey` (line 309). Neither is a timestamp key.
  - The remaining `C617.1` uses are app-container accesses by RN, Expo and AsyncStorage, which `C617.1` does cover. Today's manifest is therefore correct.
- **Risk:** a later change that reads `.contentModificationDateKey` / `.creationDateKey`, `attributesOfItem` or `stat` on a ubiquity URL would have no fitting reason code. `3B52.1` needs user-granted access through a document picker.
- **Fix** (owner `modules/icloud-sync/ios/ICloudSyncModule.swift`, comment only): above the metadata query, note "timestamps of replica files come only from NSMetadataItem attributes — do not read URLResourceKey dates/stat on ubiquity URLs (no privacy-manifest reason covers the ubiquity container)". Optionally add a `scripts/prebuild-checks/icloud.js` assertion that greps the Swift source for `contentModificationDateKey|creationDateKey|attributesOfItem|modificationDate` and fails if it finds one.

#### R3-3 · The inline-modules group sits in an `objectVersion = 54` project — P2 (known, verify on EAS)

- **Where:** in the prebuild output, `ios/Mandarat.xcodeproj/project.pbxproj:6` reads `objectVersion = 54`, and lines 197-199 and 671-682 hold the `PBXFileSystemSynchronizedRootGroup` (`path = ../native/ios`, `sourceTree = SOURCE_ROOT`) on target `Mandarat`.
- **Evidence:** `node_modules/@expo/inline-modules/build/xcodeProjectUpdates.js:99` adds the group without raising `objectVersion`. Xcode 16 introduced synchronized groups in format 77. V3-B.md:38 already records this risk. If Xcode silently ignores the group, it does not compile `AppIntents.swift` / `TodayStore.swift` and Siri shortcuts disappear without a build error.
- **Fix:** no code change now. Add a step to the device-QA list (`docs/v2/device-tests.md`, Siri section): on the first EAS preview build, check the build log for `AppIntents.swift` compiling, and check that the Shortcuts app lists the 4 App Shortcuts. If either fails, a fix package adds `plugins/withObjectVersion.js` (a `withXcodeProject` that sets `objectVersion = 77` and `preferredProjectObjectVersion = 77`) to `app.json` plugins. That plugin must run after the inline-modules step.

#### R3-4 · The widget extension version comes from `ios.buildNumber`, but EAS uses remote auto-increment — P2 (verify on EAS)

- **Where:**
  - In the prebuild output, `ios/ExpoWidgetsTarget/Info.plist` hardcodes `CFBundleVersion` to `1` and `CFBundleShortVersionString` to `1.0.0`. These are literal values, not `$(CURRENT_PROJECT_VERSION)`.
  - `node_modules/expo-widgets/plugin/build/ios/withWidgetSourceFiles.js:102` writes them from `config.ios?.buildNumber ?? '1'`.
  - `eas.json:4` sets `appVersionSource: remote` and `eas.json:28` sets `autoIncrement`.
- **Evidence:** the app config has no `ios.buildNumber`. If EAS sets the remote build number only on the main target's Info.plist, the appex keeps `1`. App Store Connect then sends ITMS-90473 ("CFBundleVersion of extension does not match its containing app"). That is a warning today, but it is listed for enforcement.
- **Fix:** on the first EAS preview build, unzip the IPA and compare `Payload/Mandarat.app/Info.plist` with `PlugIns/ExpoWidgetsTarget.appex/Info.plist`. If they differ, a fix package extends `plugins/withWidgetStrings.js`: in a `withDangerousMod` that runs after expo-widgets, set the two keys in `ios/ExpoWidgetsTarget/Info.plist` to `$(CURRENT_PROJECT_VERSION)` and `$(MARKETING_VERSION)`. EAS writes the build settings for every target it signs, and `appExtensions` already lists the widget.

#### R3-5 · The widget extension's display name is the literal `ExpoWidgetsTarget` — P2

- **Fix** (owner `plugins/withWidgetStrings.js`, `withXcodeProject`): for the `ExpoWidgetsTarget` build configurations, set `INFOPLIST_KEY_CFBundleDisplayName = "만다라트"`. Optionally also write `CFBundleDisplayName` into the three widget `<lang>.lproj/InfoPlist.strings` files with the `locales/*.json` names. Add an assertion to `scripts/prebuild-checks/widgets.js`.

#### R2-1 · The Android launcher label is "Mandarat" in every language — P2

- **Where:**
  - The Android prebuild writes `android/app/src/main/res/values/strings.xml` as `app_name = Mandarat`, from `app.json:3` (`name`).
  - `values-b+ko`, `values-b+ja` and `values-b+en` are each written as an empty `<resources/>`.
  - The cause is that `locales/{ko,ja,en}.json` have only an `ios` block.
- **Evidence:** `node_modules/@expo/config-plugins/build/android/Locales.js:64-78` writes `values-b+<lang>/strings.xml` only from the `android` block of each locale file. The Android home screen therefore shows "Mandarat", which matches neither 만다라트 nor Mandalart nor マンダラート. It also ignores the ko fallback (owner confirmation 3).
- **Fix:**
  1. Add `"android": { "app_name": "만다라트" }` to `locales/ko.json`, `"android": { "app_name": "マンダラート" }` to `locales/ja.json` and `"android": { "app_name": "Mandalart" }` to `locales/en.json`. Do not change `app.json` `name`, because it sets the Xcode target name `Mandarat` that `scripts/prebuild-checks` relies on.
  2. Optional: for other device languages, set the default `values/strings.xml` `app_name` to 만다라트 with a small `withStringsXml` plugin, `plugins/withAndroidName.js`.

#### R2-2 · The Language footnote names the iPhone on web and Android — P2

- **Where:** `src/screens/settings/LanguageSection.tsx:79` and `src/i18n/{ko,ja,en}/lang.ts` (`footnote`).

#### R2-3 · The web `document.title` stays 만다라트 in ja and en — P2

- **Where:** `src/i18n/react.tsx:27-29` (`markDocument`). The static `<title>` is in `public/index.html`.
- **Evidence:** a Playwright probe of `/?lang=ja` and `/?lang=en` returned `page.title()` = `만다라트` for both. The tab title and the bookmark name are Korean while the app is in ja or en.
- **Fix** (owner `src/i18n/react.tsx`): in `markDocument`, also set `document.title = msg(l).settings.appName`. That key already exists in all three catalogs and gives 만다라트 / マンダラート / Mandalart.

#### R2-4 · Android manifest permissions — P2 (Android is not a store target)

- **Where:** in the Android prebuild, `AndroidManifest.xml` contains `SYSTEM_ALERT_WINDOW`, `READ_EXTERNAL_STORAGE` and `WRITE_EXTERNAL_STORAGE` (maxSdk 32). It also contains `expo.modules.updates.*` meta-data, although `expo-updates` is not a dependency.
- **Evidence:** these are template defaults. The app needs none of these permissions.
- **Fix** (owner `app.json`, only if an Android build is ever shipped): add `"android": { "blockedPermissions": ["android.permission.SYSTEM_ALERT_WINDOW", "android.permission.READ_EXTERNAL_STORAGE", "android.permission.WRITE_EXTERNAL_STORAGE"] }`.

#### R3-6 · `extra.eas.projectId` is missing — P2 (owner setup)

- **Evidence:** the first `eas build` (plan §8) runs `eas init` interactively and writes `extra.eas.projectId` into `app.json`. This is expected, but the owner should commit that edit so later EAS Workflows (`.eas/workflows/e2e-ios.yml`) run non-interactively.
